## 1. Цель и подход

Assetrix — быстрый инструмент IT-техника для учёта активов со смартфона: QR/штрихкод, пакетные операции, неизменяемая история.

**Подход:** сделать «на коленке», но готовое к работе → испытывать на реальных задачах → дорабатывать итерациями → перенести на Rust + PostgreSQL → пометить готовым → следующий инструмент.

**Первый объём:** IT-железо IT-отдела — учёт кодов и инвентарных номеров, выдача и возврат, инвентаризация.

**Метрики:**
- одиночная операция со смартфона — 3–5 с;
- отклик на скан в пакетном режиме — ≤ 1 с;
- объём: до 50 000 активов, сотни сотрудников, десятки отделов, сотни кабинетов.

## 2. Этапы

| Этап | Цель | Объём |
|---|---|---|
| **P1.0** | Учёт, выдача и возврат IT-железа | Разделы 4–9 этого документа |
| **P1.1** | Инвентаризация | Режим сверки (раздел 6.4) |
| **P1.x** | Доработки по итогам испытаний | Из Backlog; в том числе подсказка о переносе активов при смене отдела сотрудника (раздел 5.4) |
| **P2** | Движение оборудования | Комплекты при приёме, список при увольнении, подменный фонд на время ремонта, передача с подтверждением получателем (`transit`), вход и роли |
| **P3** | Лицензии и сертификаты | Лицензии как активы: выдача человеку или привязка к активу, места, сроки, очередь на приостановку при возврате |
| **R** | Перенос | Rust (Axum + Askama + htmx, sqlx) + PostgreSQL, когда схема перестанет меняться |

Rust-трек (утилита QR-генератора) идёт параллельно и пилот не блокирует.

## 4. Модель данных

### 4.1. Asset

| Поле | Тип | Обязательное | Комментарий |
|---|---|---|---|
| `id` | UUID | да | Внутренний, не показывается |
| `asset_code` | text, unique | да | Собственный код Assetrix, кодируется в QR (раздел 4.3) |
| `name` | text | да | |
| `category_id` | FK → `categories` | да | Тип оборудования (ноутбук, монитор…), пользовательский справочник |
| `ledger_type_id` | FK → `ledger_types` | нет | Тип актива по бухгалтерии (Ledger / Axapta) |
| `manufacturer` | text | нет | |
| `model` | text | нет | |
| `purchase_date` | date | нет | |
| `initial_cost` | decimal | нет | Начальная стоимость; валюта — настройка системы |
| `organization_id` | FK → `organizations` | нет | Юрлицо-владелец; пусто — например, личное имущество |
| `attributes` | JSON | нет | Параметры из Excel (CPU, RAM…), пока без схемы — см. Backlog «категоризация» |
| `note` | text | нет | |
| `created_at`, `created_by` | | да | |

**Кеш состояния** (выводится из событий, пересчитывается командой recalculate):
`physical_condition`, `operational_status`, `holder_type` (`person` | `department`), `holder_id`, `department_id` (баланс), `warehouse_id`, `location_id`, `last_event_id`.

Инвентарный номер, серийник и прочие внешние коды хранятся не в полях актива, а в таблице идентификаторов (4.2).

### 4.2. Внешние идентификаторы

- **`identifier_schemes`** — `id`, `key`, `name`, `pattern` (regex, необязательно), `is_unique` (bool), `is_sensitive` (bool).
  - Начальный набор: `invent_num` (unique), `hostname`, `service_tag`, `serial_num`, `license_key` (sensitive), `vin_code`.
  - Схемы — пользовательский справочник: добавляются и меняются без изменения кода.
  - `is_unique` не блокирует ввод, а предупреждает о дубле: в реальных данных встречаются повторы инвентарных номеров (D16).
- **`identifiers`** — `asset_id`, `scheme_id`, `value` (как введено), `normalized_value` (верхний регистр, без пробелов, `-`, `.`).
  - У актива может быть сколько угодно идентификаторов, в том числе ни одного: например, личный компьютер без инвентарного номера.
  - Номер может появиться позже: например, после «ремонта» (сборки нового ПК под старым номером).
- Значения схем с `is_sensitive` не выводятся в списках и не печатаются.
- Изменение идентификаторов — событие `UPDATED`.

### 4.3. Собственный код (`asset_code`)

- **Алфавит:** Crockford Base32 (`0-9 A-Z` без `I L O U`).
- **Длина:** 7 случайных символов + 1 контрольный (Luhn mod 32). Это ≈ 34 млрд значений; при вставке выполняется проверка на коллизию.
- **Отображение:** `K7F2-9QXM`.
- **Ввод:** регистр и `-` игнорируются; `O`→`0`, `I`/`L`→`1`.
- **В QR кодируется URL:** `https://<хост>/a/K7F29QXM`. Обычная камера телефона открывает карточку актива, а сканер Assetrix извлекает код из URL.
- Формат предварительный и проверяется на пилоте.

### 4.4. Справочники и оргструктура

| Сущность | Поля | Комментарий |
|---|---|---|
| `organizations` | `id`, `name` | Юрлица группы компаний |
| `categories` | `id`, `name` (unique) | Плоский справочник |
| `ledger_types` | `id`, `code`, `name` | Типы активов по бухгалтерии |
| `departments` | `id`, `name`, `organization_id` | |
| `persons` | `id`, `full_name`, `department_id`, `external_id` (ID в Vikarina), `login` (AD), `email`, `is_active` | Источник — Vikarina (MS SQL); `login` нужен для сопоставления владельцев при импорте |
| `locations` | `id`, `parent_id`, `name`, `kind` (`site`/`building`/`floor`/`room`/`other`) | Дерево произвольной глубины |
| `warehouses` | `id`, `name`, `kind` (`virtual`/`physical`), `location_id` (необязательно), `is_archived` | Раздел 4.5 |
| `department_warehouses` | `department_id`, `warehouse_id`, `is_default` | Связь многие-ко-многим |

Справочники и оргструктура — обычные таблицы. Event sourcing строго применяется к активам. Удаление записей, на которые ссылаются события, заменяется архивацией.

### 4.5. Склады

- Склад всегда опционален: у отдела может не быть склада, может быть один или несколько. Один склад могут использовать несколько отделов.
- При создании отдела ему автоматически создаётся виртуальный склад (`is_default`). Его можно удалить или заменить.
- Вид склада переключается `virtual` ↔ `physical`.
- **Админка складов в P1.0:** создание, переименование, смена вида, привязка к отделам, архивация. Удалить можно только пустой склад без истории; иначе склад архивируется.
- **Не в P1 (pro, D10):**
  - адресация физического склада: зоны, улицы, стеллажи, этажи, места;
  - распределение по местам хранения;
  - учёт условий хранения: влажность, температура, сроки, периодические манипуляции.
- При переключении `physical` → `virtual` адресация, когда она появится, может теряться. Система должна предупреждать об этом.

### 4.6. Event

| Поле | Комментарий |
|---|---|
| `seq` | INTEGER PK, глобальный порядок |
| `id` | UUID |

Изменение и удаление событий запрещено:
- в БД — триггерами `BEFORE UPDATE` и `BEFORE DELETE`, которые выбрасывают ошибку;

Таблица `users` есть с самого начала. В P1 в ней одна запись — системный пользователь, а `created_by` всегда заполнено.

## 5. Состояние актива и переходы

### 5.1. Измерения состояния

| Измерение | Значения | Смысл |
|---|---|---|
| `physical_condition` | `virtual`, `active`, `maintenance`, `damaged`, `teardown`, `scrap`, `disposed` | Физическое состояние |
| `operational_status` | `available`, `assigned`, `reserved`, `transit`, `lost`, `write_off` | Операционный статус |
| Держатель (holder) | сотрудник или отдел | Кто отвечает за актив |
| Баланс (`department_id`) | отдел | На каком отделе числится юридически; при выдаче — отдел сотрудника |
| Склад (`warehouse_id`) | склад или пусто | Где хранится, если хранится на складе |
| Местоположение (`location_id`) | узел дерева или пусто | Где физически находится |

Склад и местоположение — не держатели. Они ничего не говорят о том, кто отвечает за актив.

В P1 используются только часть значений:
- `reserved`, `transit` — появятся в P2;
- `virtual` — в P3;
- `lost` — в P1.1 (по итогам инвентаризации).

### 5.2. События P1

| Событие | Допустимо, когда | Результат |
|---|---|---|
| `CREATED` | — | `active` + `available`; держатель — отдел из контекста; склад и местоположение — из контекста, если указаны |
| `UPDATED` | Всегда | Меняются атрибуты или идентификаторы; diff пишется в `payload` |
| `ASSIGNED` | `available`, или `assigned` (переназначение); физическое состояние не `teardown`/`scrap`/`disposed` | `assigned`; держатель — сотрудник; баланс — отдел сотрудника. Склад и местоположение не меняются, если пользователь явно не выбрал иное (5.3) |
| `RETURNED` | `assigned` | `available`; держатель — отдел из контекста (по умолчанию — баланс); склад — из контекста, если указан |
| `TRANSFERRED` | `available` | Держатель и баланс → другой отдел |
| `MOVED` | Кроме `disposed` | Меняются только склад и/или местоположение |
| `SENT_TO_REPAIR` | Физическое состояние `active` или `damaged` | `maintenance`. Внешний сервис: держатель не меняется, сервис пишется в `payload`. Внутренний ремонт: держатель → ремонтирующий (сотрудник или отдел, обычно IT), прежний держатель — в `payload` |
| `RETURNED_FROM_REPAIR` | `maintenance` | `active` или `damaged` (из контекста). Держатель по умолчанию — прежний, из события `SENT_TO_REPAIR` |
| `CONDITION_CHANGED` | Кроме `disposed` | Физическое состояние → `damaged` / `teardown` / `scrap` / `disposed` / `active` |
| `WRITTEN_OFF` | Не `assigned` и не `write_off` | `write_off`; физическое состояние — из контекста (по умолчанию не меняется) |
| `CORRECTED` | Всегда | Ручная установка любых полей состояния с обязательной причиной. Обходит проверки переходов и выделяется в истории |
| `FOUND` / `MARKED_LOST` | P1.1 | См. 6.4 |

После `write_off` допустимы только `UPDATED`, `MOVED`, `CONDITION_CHANGED` и `CORRECTED`.

### 5.3. Подсказка о складе при выдаче

При `ASSIGNED` система спрашивает: «Переместить на склад отдела?» По умолчанию — нет, ничего не перемещается.

### 5.4. Смена отдела сотрудника (P1.x)

При изменении отдела сотрудника система показывает активы, которые за ним числятся. По каждому активу можно выбрать:
- «оставить за сотрудником» — `TRANSFERRED` баланса на новый отдел (типичный случай для ноутбука);
- «вернуть отделу» — `RETURNED` (типичный случай для стационарного ПК, который остаётся на месте).

По умолчанию ничего не меняется.

## 6. Сканирование

### 6.1. Поиск по скану

1. Нормализовать ввод; если это URL Assetrix — извлечь код.
2. Искать сначала по `asset_code`, затем по `identifiers.normalized_value`.
3. Если найдено несколько активов — предложить выбор.
4. Если не найдено ничего — предложить: создать / игнорировать / в список ожидания (pending).

### 6.2. Устройства ввода

- **Камера** телефона или веб-камера: `BarcodeDetector` с полифилом.
- **USB-сканер:** ввод с клавиатуры, конец кода — Enter.
- **Обратная связь:** звук, вибрация (где доступна) и цвет на каждый скан.

### 6.3. Scan session (P1.0)

| Режим | Контекст (задаётся до сканирования) |
|---|---|
| `ASSIGN` | Сотрудник; «переместить на склад отдела» (по умолчанию нет) |
| `RETURN` | Отдел (по умолчанию — баланс); склад (необязательно) |
| `MOVE` | Склад и/или местоположение |
| `SEND_TO_REPAIR` | Внешний сервис (название) или внутренний ремонтирующий |
| `RETURN_FROM_REPAIR` | Результирующее состояние; держатель (по умолчанию — прежний) |

Правила:
- До 50 позиций в сессии. Повторный скан игнорируется. Позицию можно удалить.
- Каждый скан проверяется сразу: недопустимые позиции подсвечиваются красным и не применяются.
- «Применить» — одна транзакция для всех допустимых позиций, общий `operation_id`. Повторное применение блокируется `idempotency_key`.
- Сессия хранится на сервере: перезагрузка страницы её не теряет.

### 6.4. Инвентаризация (P1.1)

- **Режим `INVENTORY`.** Область сверки — местоположение (с поддеревом), склад или отдел.
- **Результат:** найдено / не найдено / лишнее.
- **Действия по итогам, одной кнопкой:**
  - найденные → `FOUND`; если местоположение отличается — дополнительно `MOVED`;
  - не найденные → `MARKED_LOST` (`lost`);
  - лишние → `MOVED` в область сверки.
- Отчёт о сверке сохраняется.

## 7. Наклейки

- **Печать:** HTML-страница с CSS `@page`, через диалог печати браузера. Этот же диалог отправляет на принтер или сохраняет в PDF.
- **Шаблоны:**
  - одна наклейка (размер задаётся настройкой; до покупки принтера — 50×25 мм);
  - лист A4 с сеткой наклеек.
- **Содержимое:** QR (URL), `asset_code` крупно, `invent_num` мелко, если есть. Название компании не печатается — его передаёт оформление наклейки.
- **Пакетная печать:** из выборки в списке активов.
- **Позже:** серверный PDF (утилита PDF-конвертера); прямая печать на сетевой принтер (ZPL).

**Критерии выбора принтера:**
- термотрансфер с риббоном, а не прямая термопечать;
- полиэстер + смоляной (resin) риббон;
- 300 dpi;
- Ethernet или Wi-Fi;
- поддержка ZPL (родная или эмуляция).

## 8. Импорт

- **CLI:** `assetrix import assets <file.xlsx|csv> --map <mapping.toml> [--dry-run]`.
  - Конфиг сопоставляет колонки с полями, схемами идентификаторов и `attributes`.
  - Ключ для повторного запуска (upsert) задаётся в конфиге, например `invent_num` или `serial_num`.
  - Каждый новый актив получает `CREATED` с `payload.source = "import"`.
  - Режим `--dry-run` выдаёт отчёт: создать / обновить / ошибки.
- **Источник активов в P1** — Excel IT-отдела (`Spare.xlsx`, лист `Summary`). Маппинг колонок, статусов и открытые вопросы — в [`import_mapping_spare.md`](import_mapping_spare.md). Axapta — источник для будущей системы и в P1 не импортируется.
- **Общие правила очистки:** `N/A` и пустые ячейки → нет значения; многострочные ячейки сохраняются как есть; даты Excel (serial) → ISO.
- **Лицензионные ключи** (Windows, Office) в P1 не импортируются (D14). Лист `Office` — входные данные для P3.
- **Исходные файлы с реальными данными не коммитятся** (D15).
- **Сотрудники:** CSV-выгрузка из Vikarina (SQL-запрос) → `assetrix import persons`.
  - Upsert по `external_id`.
  - Отделы создаются по названию; вместе с отделом создаётся его виртуальный склад.

## 9. Доступ и роли

- **P1:** один пользователь, без входа. Защиту в сети даёт `basic_auth` в Caddy.
- **P2:** вход и роли. Роль — набор прав (`asset.assign`, `asset.write_off`, `inventory.run`, `transfer.confirm`…), а не код.
- **Роли (названия рабочие):**

| Роль | Права |
|---|---|
| `admin` | Администрирование системы |
| `it` | Управление IT-активами |
| `manager` / `dept_head` | Запросы на оборудование, инвентаризация |
| `accountant` | Постановка на баланс, списание, инвентаризация, остаточная стоимость |
| `storekeeper` / `logistics` | Приёмка, отгрузка, утилизация, перемещения, инвентаризация |
| `employee` | Только чтение: своё и своего отдела; подтверждение получения при передаче |

## 10. Надёжность

- События неизменяемы (4.6).
- Команда recalculate пересчитывает кеш из лога и показывает расхождения.
- Пакетные операции идемпотентны (6.3).
- Ошибки не замалчиваются: каждая отклонённая позиция показывается с причиной.
- Ежедневный бэкап SQLite.

## 11. Definition of Done

### P1.0

1. `docker compose up` разворачивает систему на Linux-хосте.
2. Телефон открывает её по имени `*.lab.<домен>` с валидным HTTPS — дома и на работе.
3. Камера телефона (Android и iOS) и USB-сканер находят актив по QR, `invent_num` и серийнику.
4. Реальные данные импортированы из Excel IT-отдела; сотрудники — из выгрузки Vikarina.
5. Работает админка складов и местоположений (4.5).
6. Наклейки печатаются: одна и листом A4.
7. Пакетная выдача 10 устройств: отклик на каждый скан ≤ 1 с; одиночная операция из карточки — 3–5 с.
8. Возврат, перемещение и ремонт отрабатывают по таблице 5.2. Запрещённые переходы отклоняются, и это покрыто тестами.
9. `UPDATE`/`DELETE` событий отклоняются и в API (405), и триггером в БД.
10. Recalculate не находит расхождений с кешем.
11. Неделя реального использования.

### P1.1

1. Сверка кабинета (≥ 20 активов) даёт корректный отчёт: найдено / не найдено / лишнее.
2. События по итогам создаются одной кнопкой.
3. Проведена хотя бы одна реальная инвентаризация.

## 12. Вне объёма P1

- Вход, роли, несколько пользователей (→ P2).
- Адресация складов, распределение, условия хранения (→ pro).
- Лицензии и сертификаты (→ P3).
- Комплектующие и сборки: связи «актив в составе актива», `INSTALLED`/`REMOVED`.
- Передача с подтверждением получателем, резерв (→ P2).
- Интеграции с Axapta и AD; живая синхронизация с Vikarina.
- Оффлайн, расходные материалы, закупки.

## 13. Заметки для FlowERP

- При изменениях в штатном расписании (перевод, увольнение) всегда предлагать решение по активам, закреплённым за сотрудником.
- Источник бухгалтерии — Axapta: история покупки, постановка на баланс, изменения стоимости. В будущем — продукция с цепочкой «материалы → заготовки → детали → узлы».
