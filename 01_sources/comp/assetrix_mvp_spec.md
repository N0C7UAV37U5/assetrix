# Design & Scope: Assetrix (MVP)

## 1. Обзор проекта (Executive Summary)
**Assetrix** — это часть экосистемы проекта Mycorium - специализированное PWA-решение для системных администраторов и IT-инженеров. Основной акцент сделан на **скорости операций** (3–5 секунд на действие) и **надежности данных** через механизм Event Sourcing.

* **Проблема:** Корпоративные системы учета слишком громоздки для быстрых перемещений «на бегу».
* **Решение:** Мобильное приложение с мгновенным сканированием и пакетной обработкой.

---

## 2. Архитектура системы
Система строится на принципах **Event Sourcing**. Каждое изменение состояния — это неудаляемая запись в логе.

### Технологический стек
| Слой | Технология | Обоснование |
| :--- | :--- | :--- |
| **Database** | PostgreSQL | Надежная поддержка JSONB для метаданных событий. |
| **Frontend** | PWA (Browser) | Доступ к камере, работа без Store, mobile-first. |
| **Backend** | FastAPI (Python) | Высокая скорость разработки и производительность. |
| **Infrastructure** | Docker + Caddy | Легкое развертывание (`docker-compose up`), автоматический HTTPS. |

## 3. Модель данных (Data Model)

### 3.1. Основные сущности
* **Device (Asset):** Хранит статические данные и кэшированное (derived) состояние для быстрого поиска.
* **DeviceType:** Пользовательский справочник типов без иерархии (ноутбук, монитор и т.д.).
* **Event (Immutable Log):** Главный источник истины. Неизменяем. NO update/delete.

### 3.2. Dual Status Model (Критическая логика)
У каждого устройства есть два независимых вектора состояния:

| Физическое состояние (Physical) | Операционный статус (Operational) |
| :--- | :--- |
| virtual, active, maintenance, damaged, teardown, scrap, disposed | available, assigned, reserved, transit, lost, write_off |

**Правило:** Текущее состояние = Derived из последнего события. Возможны комбинации вроде `assigned` (у сотрудника) + `damaged` (разбит экран).

## 4. Спецификация событий (Event Types)
Для MVP реализуются следующие типы событий:
* `CREATED`
* `ASSIGNED`
* `RETURNED`
* `SENT_TO_REPAIR` / `RETURNED_FROM_REPAIR`
* `WRITTEN_OFF`

## 5. Функциональный объем (Scope)

### Входит в MVP (In-Scope)
* **Сканирование:** Поддержка камер смартфонов, веб-камер и USB-сканеров (эмуляция клавиатуры).
* **Scan Sessions (Core):** Универсальная пакетная обработка (выбрал режим -> отсканировал группу -> применил действие одной кнопкой).
* **Управление:** Создание устройств, просмотр списка с фильтрацией и истории событий.
* **История:** Просмотр ленты событий для каждого устройства без возможности редактирования.
* **Валидация:** Проверка недопустимых переходов состояний (бизнес-логика).
* **Поиск:** Фильтрация по серийнику, тегу или типу.

### НЕ входит в MVP (Out-of-Scope)
* Многопользовательский доступ и роли (все действия от одного системного пользователя);
* Интеграция с Active Directory / LDAP;
* управление закупками; 
* расходные материалы;
* Оффлайн-режим.

---

## 6. UX/UI Принципы
* **Мобильность:** Интерфейс оптимизирован под управление одной рукой. Все основные кнопки управления находятся в нижней части экрана (зона большого пальца).
* **Правило 3 кликов** Любое стандартное действие (приемка/выдача) должно укладываться в 3 нажатия.
* **Обратная связь:** Звуковая и визуальная индикация при каждом успешном сканировании.

## 7. Техническая реализация (Developer Notes)

### Структура БД (Примерная)
```sql
-- Пример таблицы событий
CREATE TABLE events (
    id UUID PRIMARY KEY,
    device_id UUID REFERENCES devices(id),
    event_type VARCHAR(50),
    meta JSONB, -- Сюда пишем context (assignee_id, repair_company и т.д.)
    created_at TIMESTAMP DEFAULT NOW(),
    created_by VARCHAR(100)
);

-- Таблица устройств с кэшем состояния
CREATE TABLE devices (
    id UUID PRIMARY KEY,
    asset_tag VARCHAR(100),
    serial_number VARCHAR(100) NOT NULL,
    physical_condition VARCHAR(50), -- cached
    operational_status VARCHAR(50), -- cached
    last_event_id UUID
);
```

## 8. Definition of Done (Критерии готовности)
1. Система разворачивается через `docker-compose up`.
2. Приложение открывается по локальному IP на смартфоне.
3. Камера успешно распознает QR-код и открывает карточку девайса.
4. Сканирование QR мгновенно находит устройство или предлагает создать новое.
5. Создано 10 устройств, проведена пакетная операция ASSIGN.
6. Массовые операции (Scan Sessions) корректно генерируют цепочку событий в БД.
7. В базе данных зафиксированы события, состояние Device обновилось в кэше.
8. Кэшированное состояние в таблице `devices` всегда соответствует последнему событию.
9. Попытка удалить или изменить событие через API невозможна (ошибка 405/403).
