## 1. Лист `Summary` — оборудование (P1.0)

212 строк. Сами строки бывают трёх видов:

| Вид | Сколько | Признак |
|---|---|---|
| Учтённые активы | ~76 | Есть `InventNr`, обычно есть `Status` |
| Хосты с типом, но без инв. номера | ~75 | Есть `Host type`, нет `InventNr` |
| Только сетевые данные | ~61 | Заполнены только `Host name` и описания из Axence / AD |

### 1.1. Колонки

| Колонка | Заполнено | Куда | Обработка |
|---|---|---|---|
| `InventNr` | 76 | Идентификатор `invent_num` | Формат `NN-NNNN`. **Есть 2 дубля** → уникальность только предупреждает (D16) |
| `Host name` | 203 | Идентификатор `hostname` (новая схема) | `N/A` и пусто → нет значения. Используется и как `name`, если нет лучшего |
| `Host description Axence` | 201 | `attributes.axence_description` | Описание из сетевой инвентаризации Axence nVision |
| `Host description AD` | 76 | `attributes.ad_description` | |
| `Host type` | 149 | `category` | `Desktop`, `Laptop`, `Micro`, `Mono` (моноблок); пусто → категория `Unknown` |
| `MB make` | 132 | `model` | У ноутбуков это модель, у десктопов — материнская плата. Дополнительно копируется в `attributes.mb_make` |
| `Processor` | 77 | `attributes.cpu` | |
| `RAM (make \| qty \| frqnc)` | 48 | `attributes.ram` | Строки внутри ячейки — отдельные модули; в будущем — комплектующие |
| `Storage (type\|make\|qty)` | 47 | `attributes.storage` | Аналогично RAM |
| `Serial Nr` | 58 | Идентификатор `serial_num` | `N/A` → нет значения. Форматы разные (15 цифр, 8 символов и т.д.) |
| `Last owner` | 63 | Держатель — сотрудник (если найден по `login`) | Это AD-логин (`имя.фамилия`). Не найден → `attributes.legacy_owner` |
| `Windows version` | 70 | `attributes.windows_version` | Бывает несколько строк (история апгрейдов) — сохраняется как есть |
| `Windows Code` | 63 | **Не импортируется в P1** (D14) | Лицензионный ключ |
| `Office version` | 62 | `attributes.office_version` | Часто «версия + инв. номер ПК-донора» (`2016 NN-NNNN`) — это привязка лицензии, данные для P3 |
| `Office Code` | 63 | **Не импортируется в P1** (D14) | Лицензионный ключ |
| `Bitlocker` | 106 | `attributes.bitlocker` | `ON`/`On` → `on`; `Exclude` → `exclude` (нет TPM ни аппаратного, ни программного — ПК в списке исключений правила обязательного Bitlocker на портале infra). Устаревшая отметка, логики на неё не завязываем |
| `Comments` | 31 | `note` | Иногда содержит местоположение — местоположения заводятся вручную |
| `Status` | 76 | Состояние (1.2) | |

### 1.2. Статусы

| `Status` | Строк | Состояние после импорта | Смысл |
|---|---|---|---|
| `Active` | 42 | `active`; `assigned`, если `Last owner` найден, иначе `available` | В работе |
| `Spare` | 2 | `active` + `available` | Резерв |
| `Damaged` | 7 | `damaged` + `available` | Повреждён |
| `Disabled` | 24 | `active` + `available` + `attributes.ad_disabled = true` | Отключён от AD, не используется, все лицензии сняты. Среди них — кандидаты в доноры запчастей и на списание; решение принимается вручную после импорта |
| `Preparing` | 1 | `active` + `available`, держатель — IT-отдел | Подготовка к выдаче силами IT |
| пусто | 136 | `active` + `available` + `attributes.needs_review = true` | Импортируются все, включая «только сетевые» строки |

Строки с `needs_review` становятся первым списком для реальной инвентаризации P1.1. `Disabled` — первым списком для решения «донор / списание» (см. Backlog, «Разборка на запчасти»).

### 1.3. Ключ повторного импорта

Порядок: `invent_num` → `serial_num` → `hostname`. Строка без всех трёх пропускается и попадает в отчёт.

### 1.4. Держатель и баланс при импорте

- Держатель по умолчанию — IT-отдел; склад — его виртуальный склад по умолчанию.
- Если `Last owner` найден среди сотрудников: событие `ASSIGNED` после `CREATED`, `operation_id` общий для всего импорта.
- `Last owner` сопоставляется с `persons.login`.
- **Откуда `login`:** в Vikarina логина нет, но есть `email`, совпадающий с почтой в AD, а локальная часть адреса совпадает с AD-логином. Поэтому `login` = часть `email` до `@` в нижнем регистре.
- **Запасной вариант** (нет email): транслитерация имени и фамилии в ASCII, нижний регистр, через точку: `Ažuolas Martinkevičius` → `azuolas.martinkevicius`. Такие сопоставления помечаются в отчёте импорта как неточные.

## 2. Лист `Office` — лицензии Office (P3, сейчас не импортируется)

226 строк, по одной на ключ. Структура подтверждает модель P3 «лицензия как актив».

| Колонка | Заполнено | Смысл для P3 |
|---|---|---|
| `Office version` | 226 | `2013` / `2016` / `2019` → категория лицензии |
| `Code` | 226 | Ключ, идентификатор `license_key` (sensitive). 225 уникальных из 226 — один дубль |
| `User` | 148 | Сотрудник (ФИО) или служебная учётка `домен\имя` (6 строк) |
| `CompID` | 158 | Инв. номер ПК, к которому привязана лицензия. В основном `NN-NNNN`, есть нестандартные значения. Только ~40 из них есть в листе `Summary` |
| `Host ID` | 143 | Имя хоста — вторая привязка к ПК |
| `Status` | 182 | `Active` → привязана; `Free` → свободна; `Exclude` → ?; пусто → ? |
| `Last check date` | 166 | Дата последней проверки (Excel serial date) → «последняя сверка» лицензии |
| `Comment` | 35 | `note` |

**Выводы для P3:**
- лицензия привязывается к ПК по `invent_num` **или** `hostname`;
- ПК из `CompID`, которых нет в `Summary`, — это пробел в учёте оборудования; при импорте P3 нужен отчёт о таких расхождениях;
- нужна дата последней проверки лицензии.
